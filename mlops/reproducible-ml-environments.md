# Reproducible Environments for Machine Learning

A model experiment can change when a library version, compiler, CUDA runtime, or preprocessing dependency changes. Reproducibility means recording enough of the environment and inputs to understand and, where practical, rerun an experiment.

A random seed alone is not a reproducibility strategy.

## What to pin and record

- Python or runtime version.
- Direct and transitive package versions.
- Operating system and architecture.
- CPU/GPU type, driver, CUDA and accelerator libraries where relevant.
- Container image digest, not only a mutable tag.
- Training code commit and configuration.
- Dataset snapshot and preprocessing version.
- Random seeds and deterministic settings.
- Model artifact and evaluation outputs.

Use a dependency lockfile generated by a package manager such as uv, Poetry, or pip-tools. A broad requirement such as numpy greater than 1.0 permits many environments and is not a lock.

## Reproducibility levels

- **Environment reproducibility:** recreate the runtime and dependencies.
- **Data reproducibility:** retrieve the same source snapshot and transformations.
- **Procedural reproducibility:** rerun the same code and configuration.
- **Numerical reproducibility:** obtain identical or sufficiently close outputs.

Numerical identity can be difficult across GPU models, kernels, thread schedules, and distributed execution. Document the level you need rather than promising bit-for-bit equality without testing it.

## Practical workflow

1. Create a clean virtual environment.
2. Declare direct dependencies and generate a lockfile.
3. Build a container from a pinned base image where portability matters.
4. Record hardware and accelerator runtime details.
5. Store configuration and random seeds with the experiment.
6. Run a small smoke test in CI.
7. Rebuild from scratch periodically to catch hidden dependencies.

For PyTorch, deterministic algorithm settings can help, but may reduce performance or raise errors for operations without deterministic implementations. Consult the framework documentation for the exact version being used.

## Common pitfalls

- Using latest package versions in production builds.
- Depending on a package installed manually on one laptop.
- Pinning a CUDA package but ignoring the host driver.
- Recording only the model file and not the preprocessing pipeline.
- Assuming the same seed guarantees identical distributed GPU training.
- Putting secrets inside Docker images or committed environment files.

## Practice

Build a minimal scikit-learn project with a lockfile and a container. Record the Python version, dependency versions, dataset snapshot, and code commit. Rebuild it in a clean environment and compare the evaluation metrics.
