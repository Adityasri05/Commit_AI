# Adaptive Retrieval and Query Routing for RAG

A RAG application does not need to send every question through the same retriever. A question asking for an exact error code may benefit from lexical search, while a conceptual question may benefit from dense semantic retrieval. A structured business question may belong in a database, and an entity-relationship question may benefit from a knowledge graph.

**Query routing** selects an appropriate retrieval path for a request. It is different from query rewriting: rewriting changes the query; routing decides where and how to search.

## Retrieval routes

| Query pattern | Candidate route | Why it may help |
|---|---|---|
| Exact names, IDs, error codes | BM25 or keyword search | Preserves rare literal terms |
| Natural-language concepts | Dense vector retrieval | Matches semantic similarity |
| Mixed technical and natural language | Hybrid retrieval | Combines lexical and semantic signals |
| Structured facts and aggregates | Read-only SQL or analytics store | Uses explicit schema and exact filters |
| Entity relationships | Knowledge graph | Follows typed edges and relations |
| Recent operational state | Authoritative live API or database | Avoids stale document snapshots |

These are starting hypotheses, not universal rules. Benchmark routes on the actual corpus and query distribution.

## A routing architecture

1. Normalize the user's query without removing meaningful identifiers.
2. Estimate intent using rules, a small classifier, or a constrained model output.
3. Apply authorization and data-scope filters before retrieval.
4. Select one or more permitted retrievers.
5. Retrieve candidate passages and normalize their metadata.
6. Merge or rerank candidates when multiple routes run.
7. Pass a bounded evidence set to generation.
8. Record route choice, retrieval quality, latency, and fallback reason.

A router should be able to choose a safe fallback when confidence is low. For example, run hybrid search rather than forcing a brittle single route.

## A simple rule-based baseline

```python
import re

def choose_route(query: str) -> str:
    text = query.lower()

    if re.search(r"\b(error|exception|http)\s*\d{3,5}\b", text):
        return "keyword"
    if re.search(r"\b(count|average|sum|total|group by)\b", text):
        return "structured_readonly"
    if re.search(r"\b(connected to|relationship between|depends on)\b", text):
        return "graph"
    return "hybrid"

def retrieve(query, retrievers, authorized_scope):
    route = choose_route(query)
    retriever = retrievers.get(route, retrievers["hybrid"])

    # Authorization must be enforced by the retriever/data layer,
    # not merely described in the prompt.
    return retriever.search(query, scope=authorized_scope, top_k=8)
```

This is a transparent baseline, not a production intent classifier. The structured route must use an allowlisted, read-only query layer with parameterized inputs; never execute arbitrary model-generated SQL.

## Model-assisted routing

A small classifier or LLM can select among a finite set of routes. If using an LLM:

- Provide a short route description and allowed enum values.
- Validate the output against a schema.
- Treat the selected route as a suggestion, not an authorization decision.
- Enforce permissions and tenant filters in code.
- Use confidence thresholds and a deterministic fallback.
- Log route decisions without unnecessarily storing sensitive query content.

A router can also choose multiple retrievers for ambiguous questions. Parallel retrieval may improve recall, but increases latency and cost. Use a reranker or a calibrated merge strategy rather than concatenating unlimited results.

## Evaluate the router and retrievers separately

Build a labeled query set with examples for each route, including ambiguous and out-of-scope questions.

Measure:

- **Route accuracy:** whether the selected path is appropriate.
- **Retrieval Recall@k:** whether relevant evidence appears in the candidate set.
- **MRR or nDCG:** whether useful evidence is ranked near the top.
- **Answer groundedness:** whether generated claims are supported.
- **Fallback rate:** how often the router cannot make a confident decision.
- **Latency and cost:** including parallel calls, reranking, and database queries.
- **Safety:** whether authorization filters remain effective across every route.

Compare adaptive routing with a fixed hybrid-retrieval baseline. A more complicated router is worthwhile only if it improves quality or operational cost on representative traffic.

## Common failure modes

- Overfitting routing rules to a small hand-written query set.
- Sending an exact identifier query only to dense retrieval.
- Treating route selection as permission to access a data source.
- Allowing arbitrary SQL or graph queries generated by a model.
- Forgetting to apply tenant and document-level filters on fallback routes.
- Increasing latency with parallel retrievers that rarely add useful evidence.
- Evaluating route accuracy but not end-to-end answer quality.

## Practice

Create 40 questions across exact lookup, conceptual search, structured aggregation, relationship search, and ambiguous requests. Compare a fixed hybrid retriever with a rule-based router. Record route accuracy, Recall@5, nDCG@10, P95 latency, and the number of authorization-filter failures. The last metric must remain zero.
